# Building Combat Camera - Configurable

Use Windows x64, Visual Studio 2022 C++ build tools (MSVC 19.44), Windows SDK 10.0.26100.0, CMake 3.25 or newer, Git and Ninja. Start an **x64 Native Tools Command Prompt**. MASM is included with the C++ build tools.

Clone this repository and prepare the exact UE4SS SDK revision:

```bat
git clone https://github.com/my-mods/Dawnwalker-Combat-Camera-Configurable.git
git clone https://github.com/UE4SS-RE/RE-UE4SS.git ue4ss-sdk
git -C ue4ss-sdk checkout 97b7e501c19d8b2b7c662feee73aaa0dc1f0a4d1
git -C ue4ss-sdk config submodule.deps/first/Unreal.url https://github.com/UE4SS-RE/UEPseudo.git
git -C ue4ss-sdk submodule update --init deps/first/Unreal
```

The Unreal headers must resolve to `eb40a05f49509bdeb1ac39287032b60af585cca8`. CMake checks both revisions. It fetches the pinned MinHook and SDK header dependencies declared in `native/CMakeLists.txt`.

```bat
cd Dawnwalker-Combat-Camera-Configurable
cmake -S native -B build -G Ninja -DCMAKE_BUILD_TYPE=Release -DUE4SS_SDK=../ue4ss-sdk
cmake --build build
```

The result is `build/main.dll`. The mod uses `/MD`, C++23 and reproducible compilation/link options. `Framecore2b.def` supplies the exact imported host symbols; a complete UE4SS rebuild is unnecessary.

## Native bindings

The object-array shutdown callback disables native activity, invalidates watched identities and unregisters its deletion listener before returning. Hook teardown remains in the separate stop path; repeated cleanup does not remove the listener twice or access dying game objects.

The native settings callback consumes sixteen Lua arguments in `Settings.order`. The original nine values retain their order, including the ignored legacy `freeCamera` slot; `cameraMode`, `trackingSpeed`, `trackingResumeMs`, `lockLastAttacker`, `autoLockOnHit`, `afterTargetDeath`, and `trackingCatchup` are appended. The menu exposes fifteen controls, with Logging last. The pinned host's `get_integer` removes the value it reads, so each successive setting is read at stack index 1. This applies to both saved startup settings and Mod Setting Menu Apply.

Before installing hooks, the mod validates 33 native code ranges (19,910 bytes), three virtual-table entries and 38 patch/call-site guards in the loaded game image. Required ranges must be readable, executable where appropriate, and belong to the game allocation. Function checks cover the complete recorded unwind ranges and four explicitly bounded leaf functions, including internal instructions beyond their prologues. These ranges contain no base relocations; virtual-table targets are compared relative to the actual load address. No game executable file is opened or hashed. The reference used to establish these contracts is:

| Input | SHA-256 |
| --- | --- |
| Dawnwalker.exe, Steam build 25232147 | `cb9b7d7bd88a6754c0a9c08318aa64d5013ddfd92d5badcae84e1b4ea980dcfc` |
| Framecore 2b UE4SS.dll | `fb1839ee91f71f83d508d44a2763a15ac1bb0c5fb4e504ac0fcfca64376a054a` |
| Vercadi 1.2.1-rc6 UE4SS.dll (Nexus 1.3) | `795c3732dd4dde53d1c9210d93ae8191b983031cd275e7e1cf93fef69fad6deb` |

`GameBuild.hpp` contains game-relative addresses and instruction guards; `GameCode.hpp` records the scoped code and virtual-table contracts. Unrelated executable metadata, resources or other file differences do not disable the mod. Changed required code, moved addresses or conflicting native patches still stop startup with the failing RVA (address relative to the game image). This is not an automatic port to changed game layouts. Updating the contracts requires checking function signatures, call-site relationships, UObject member offsets, virtual method slots and assembly live-register requirements. A matching prologue alone is insufficient. Keep the reference executable hash as analysis provenance, not a runtime allowlist.

The host fingerprints above record tested files only. The mod does not read or compare the UE4SS DLL file, version or fork name at runtime. Its import library requires the C++ mod lifecycle, LuaMadeSimple stack interface and object-array APIs actually used by the source. The pinned SDK describes those C++ types and consuming Lua getters; a future incompatible ABI still requires a source rebuild. `Framecore2b.def` retains its historical name, not a runtime loader restriction. Game hook code, call-site and virtual-table contracts remain checked before native calls or writes.

Smooth tracking observes the native temporary-loss route: `LoseTargetLock` at RVA `0x5e16ff4`, its target-clear return at `0x5e17071`, and `RegainTargetLock`'s switch return at `0x5e1ccf6`. The native clear, delegates and recovery timer still run. The bridge remembers the component/actor identities through native duration plus three gameplay seconds (finite durations above zero and up to 60 seconds qualify); attempts begin only at the native regain call. It also observes a clear through the existing target setter when the living target matches the identities Smooth was following; this arms a three-gameplay-second window immediately. Dead or untracked targets and explicit unlocks do not arm it.

The existing player tick services pending recovery at most every 100 gameplay milliseconds, sharing the 50 ms wall-time selection budget. Each attempt uses the remembered actor only within the native in-range list, with at most primary/fallback singleton checks. Context byte `+0x61` disables angular rejection only for that actor; native eligibility and visibility remain. Rejection retries until the finite deadline, with no camera correction while absent. No new timer, hook, global enumeration or settings polling is added. Deletion watches reject address reuse; an initial native serial assignment is accepted and current serials are captured after selection. Owner, identity, lock-intent and settings revalidation block commits after nested cancellation. Free and Native do not arm recovery. Deletion, owner replacement, unlock, mode changes and invalid gameplay contexts cancel it.

Reacquisition restarts the smooth ramp at the current view and retains the manual-input resume delay. A successful recovery holds camera-directed searches for up to three view-update gameplay seconds, until combined angular error falls to ten degrees or manual look occurs. Recent manual input during disappearance skips that hold. Existing attacker priority is preserved when present. Logging adds `trackedClears`, `recoveryAttempts` and `recoveryUs` to the ten-second summary; all diagnostic collection remains guarded by `debugLogging`.

The camera, cone and untargeted-direction gates preserve volatile registers, SIMD values and the required comparison flags. The camera gate changes the native free-camera flag and selected camera target for the local player in Free/Smooth modes and while unlocked. Native tracking releases this suppression while a selected target is locked. When target lock is off, the direction gate replaces the computed planar XY values in XMM7/XMM8 with the current camera yaw, bypassing both persistent and temporary action-target facing. It uses 32 bytes of dedicated aligned scratch space, separate from saved volatile registers. The native output stores retain zero Z, and the native epilogue restores the caller's nonvolatile SIMD registers. Missing or nonfinite camera data retains the already computed untargeted character direction; locked modes follow the original trampoline without querying camera rotation. The cone gate modifies only the scoped native threshold comparison. The game still performs candidate scoring, combat predicates and occlusion checks.

Camera heading is queried on the gameplay thread only when the native combat-direction function requests an unlocked direction. It uses the validated player's camera manager rotation getter at vtable slot `0x820`, without a new timer, target search or actor-rotation setter. Pitch is excluded, including at vertical camera angles. Optional logging aggregates successful resolutions, fallbacks and rotation-resolution microseconds; this timing excludes the preceding ownership validation and does not measure total mod or frame time.

Last-attacker hover override observes manual pitch/yaw input at the existing view-rotation hook before Smooth adds correction. It validates the current player camera on the game thread, arms only with camera-directed targeting and a held attacker, and adds no hook or timer. The native picker keeps its normal cone for a replacement; retention of the still-valid attacker alone omits the angular test while the configured dwell completes. New hits, settings Apply, target deletion/loss, unlock and session cleanup reset override intent. Aggregate Logging adds attackerOverrides.

Automatic requests use one full native picker pass per 50 ms budget interval. When the primary pass finds nothing, the game's fallback predicate runs in the following interval; a one-element fallback check can retain the current target in the meantime. An explicit target-lock press retains immediate fallback. A pending switch also validates the current target through a one-element candidate list. Controller assistance is limited to camera-directed targeting. It computes only the current target's angle, refreshes at most every 50 ms, expires after 150 ms and requires the game's controller sensitivity branch with no mouse input.

The lock choice is owned by the local player component and survives settings Apply. Two native Blueprint thunks identify the target-lock action at the checked player graph call sites, retaining the game's existing controller and keyboard bindings. Their parameter decoding remains native. An unexpected player graph length or lock-action call site disables the mod for that session and logs the reason, allowing native input to resume. SwitchLockTarget preserves its boolean return type. Other automatic, look-axis and next/previous target requests cannot replace a fixed target or create an unlocked target. Native target clearing still performs its delegate and notification cleanup. Temporary ability locks cannot enable player targeting.

Unlocked ability focus changes also use the native controller view-blend function at RVA `0x52f028c`. A separate optional contract validates that function, the focus-entry and target-update callers, and controller slot `+0xd60`. The hook suppresses only calls returning to `0x5dec07b`, `0x5dec12b` or `0x5dff1de` for the current local player while in unlocked combat. Focus enables its own cursor, so these verified callers can retain the current view while that cursor is visible. Other controller relations, gameplay state and owner lifetime checks still apply. Locked play, other callers/controllers, worker threads and inactive contexts retain all six native arguments. The ability target is unchanged; there is no camera snapshot, delayed restoration, new timer or per-frame work. Logging aggregates `abilityViewsPrevented`. An incompatible optional route leaves the other camera and ability features available.

Native hard lock remains available to combat rules. Nine guarded native attachment stores are intercepted individually, including the direct setter, Blueprint actions, casting, abilities, threat requests, combat transitions, hard lock and target selection. Only the camera-attachment store is skipped for the controlled player when the camera policy requires detachment; the surrounding native target changes, spell behavior and notifications continue. Constructors and native detachment stores are unchanged. An already attached camera uses the native detach transition once when a free/smooth combat context is acquired or resumed. Native mode uses the verified direct attachment setter once when entering native tracking with a locked target. Camera-policy changes reconcile attachment without changing the selected enemy or rebroadcasting hard lock. There is no recurring detached-flag check or detach repair in player ticks or target events.

Free/Smooth attachment prevention includes AbilityCasting and player-controlled Synchronised combat states. Synchronised actions retain their native targeting rules. Death, menus and controller-owned cinematics remain outside the player camera context. Camera evaluation consumes an atomic opaque owner identity validated on the game thread; it performs no UObject reads, registry lookups or Lua calls and does not require the gameplay thread. Attachment events validate current ownership on the game thread; other threads use only the published identity. Owner deletion, rejected player context, master disable and shutdown revoke that identity. Logging includes aggregate attachment-prevention and initial-detach counts. The nine attachment gates preserve volatile registers, flags and XMM values; the two attachment leaves use additional stack padding for Windows x64 call alignment. Scoped native code and layout checks run before installing twenty-nine camera/targeting hooks, up to four optional ability hooks, one optional ability view-blend hook and thirty-eight core instruction guards, including the untargeted-direction output stores.

All game objects are accessed on the game thread. Persistent identities read existing object serials and are invalidated by deletion notifications; no weak-reference construction or serial allocation is used. The settings bridge uses host-registered Lua functions and the menu's documented Apply notification. Restart the game after changing native binaries or reloading mod scripts.

## Last-attacker targeting

The optional `lockLastAttacker` toggle appends one boolean to the settings ABI and defaults to false. The additional hook uses `PlayerCombatComponent::ReactToHit` at RVA `0x5e1c800`, with ABI `void(combat, animationData, attackData, response)`. The complete 1,070-byte function is validated before installing its entry detour. The mod does not own or depend on the target of the player combat virtual slot `+0x8e8`; other mods may intercept that slot while forwarding this entry. The native function already belongs to the scoped code contract. Its `InAttackData +0x28` is the attacker's combat component; component `+0xa8` gives its actor. Native block, parry and omniblock reactions use this same incoming-hit route. Original reaction parameters and output pass through unchanged.

The game-thread hook copies only validated indexed identities while the player's lock is already active, or while Automatic lock on hit permits acquisition. It never retains animation/attack/response structs, allocates a weak serial or calls the target picker within a hit reaction. Hits coalesce into one pending request, serviced after the existing native player tick. Pending state expires after one second of gameplay time if targeting remains ineligible. The request consumes the shared 50 ms selection budget and uses the native switch's in-range list with at most two single-candidate primary/fallback checks. The camera-angle rejection is disabled only for this attacker, while native predicates and occlusion still apply. Failure preserves the current selection and does not retry. A hit from the current target establishes priority without any selection pass.

A successful switch holds that enemy against camera-directed requests. Controller slowdown retains its existing cadence and camera modes retain their own policies. Pending, held and in-progress selection identities use six additional slots in the existing deletion listener. Native assignment of an initially zero serial is accepted, with deletion watches armed throughout selection to reject address/index reuse; the current serial is captured when priority is established. Unlock, disable, option changes, owner replacement and invalid contexts clear the feature state; ordinary target loss releases priority. Smooth temporary-loss recovery retains priority, while a new valid attacker can supersede it. Expired or cancelled recovery releases it. No new timer, global discovery or configuration polling is added. Logging aggregates received hits, switches, rejections and selection time; its disabled path does not collect those counters or timestamps.

## Automatic acquisition and death handoff

`autoLockOnHit` and `afterTargetDeath` append settings arguments 14 and 15; their defaults are 1 (On) and 0 (Nearest enemy), respectively. The existing hit hook can queue an unlocked attacker. Acquisition is allowed only within that validated selection scope and commits the lock through the native setter after native candidate checks. A lock-intent generation rejects writes after nested settings changes, manual lock input or owner invalidation. Disabling automatic acquisition preserves the current lock, while cancelling its pending work.

A native clear of the current target whose `CurrentState` at component offset `0xb28` is `ECombatState::Dead` (10) queues the configured handoff. Clears during synchronized actions can record the event, while selection waits for normal gameplay. Temporary loss remains distinct. Nearest selection shares the existing 50 ms budget: one primary pass, then at most one fallback pass in another interval. Readiness is bounded to three gameplay seconds outside synchronized actions. No candidate result leaves the player unlocked until a later hit or manual lock. No new recurring scheduler or settings polling is introduced.

The request disables the angular filter and camera-origin flags in its temporary context; all context fields are restored. NaN distance is rejected. ## Smooth tracking

The scoped `ProcessViewRotation` hook at RVA `0x17d22f0` uses the native `void(camera, float delta, Vec3* rotation, Vec3* input)` ABI. RebelPlayerCameraManager vtable `0x76a6c58`, slot `0x880`, retains this base implementation. The controller's rotation update calls it at `0x1600de3` with the final accumulated look input from controller offset `0x538`. Tracking accepts only that caller and a validated local player on the game thread. It changes only pitch/yaw input; the original camera modifiers and pitch/yaw/roll limit calls still run. Camera positioning, collision and zoom remain in the native camera stack.

Look input is observed after native deadzones. Controller aim slowdown multiplies input by a strictly positive factor, preserving whether input is zero, so manual override also works with slowdown enabled. Tracking yields on either nonzero look axis, waits for `trackingResumeMs`, then integrates a linear 200 ms engagement ramp. At speed fraction `s`, exponential responsiveness is `8s` per second and the combined angular-speed limit is `180s` degrees/second. `trackingCatchup` defaults to 300 and ranges from 100 (Off) to 500. For combined shortest pitch/yaw error `e`, let `t = clamp((e - 45) / 135, 0, 1)`. Multiply both responsiveness and the angular-speed cap by `1 + (trackingCatchup / 100 - 1) * t*t*(3 - 2*t)`. Close following and the engagement ramp remain unchanged; the exponential step never overshoots. Valid frame deltas are capped at 50 ms; invalid deltas or stalls over 250 ms clear timing without a correction. Each update starts from the current view and computes the selected target's error relative to the current camera. It does not retain rotation pointers or write actor rotation directly.

Only Smooth while locked enters this helper. Each eligible update performs at most one current-target aim-point query and two camera getters, with no global searches, native target selection or configuration I/O. Target component and actor identities use the existing deletion listener. Target changes restart the engagement ramp; invalid contexts clear tracking. Optional diagnostics aggregate tracking steps, corrections, manual-input frames and total helper time; disabled Logging performs no tracking timer/counter work for diagnostics.


## Unlocked ability routing

Four optional hooks cover native ability validation (`0x5d9e0c0`), planning (`0x5e06dc8`), direct instant execution (`0x5df1580`) and focus actor resolution (`0x5df8810`). All four functions belong to the existing seven-range optional code contract. Opening the wheel performs no additional selection. For the unlocked local combat player, validation first uses the component owner's native no-target reference. An accepted self-centered cast needs no enemy. After a rejection, the same native level/type dispatch used by the validator identifies whether a primary target is required. Self (1) and unknown types retain the rejection without selection. Single (0), All (2) and AoE (3) reject their owner as a primary target in native code and permit a camera-directed enemy query. While unlocked, any supplied focus actor is ignored: the primary enemy comes from the native camera selector and must pass the complete native ability validator again. Explicitly locked casts retain native target handling. Costs, cooldowns, form, equipment, distance and custom restrictions are never overridden. Some area attacks require a primary enemy and retain that requirement.

Planning and direct instant execution refresh camera selection and repeat validation before entering the native operation. Both scope the focus getter to the validated actor. The native getter normally returns the owner when its stored target is empty, so direct instant execution must be intercepted independently of planning. Planning covers every focus mode within the managed player context; an instant call nested in the same plan reuses its actor without another query. Explicitly locked activation and activation outside combat validate the existing native focus actor without camera selection. Missing enemies and failed native checks stop before the native operation; legitimate self casts remain available. Session, lock-intent or actor invalidation during a scope returns no actor instead of falling back to the player. No persistent focus/combat target or new timer is written. The native SpellAbilityBase validator at `0x5deea44` is a 29-byte wrapper that forwards all five arguments to the base validator and normalizes its boolean result. The guard recognizes this wrapper only after validating its complete code under a separate optional contract. A changed wrapper leaves base ability routing and camera features available. Other specialised validation overrides, non-player calls, calls outside the managed player context and disabled behavior retain native handling. Ordinary untargeted attacks remain intact. Logging adds the guarded aggregate `abilityRejected` count and bounded activation events containing the ability name, validator address relative to the game module, target and player object indices, lock/focus mode, native reason and routing outcome. Names resolve through the host UObject API only after indexed identity validation. The event limit is 16 per ten seconds; suppressed events are counted. Logging Off performs no event name resolution, formatting or rate-limit timing. Validation events do not establish final gameplay effect or health-cost delivery.

Enemy queries use the existing native selector with camera preference, configured cone and native range/visibility checks. Its setter is intercepted synchronously to capture the indexed component identity without publishing a combat target or changing lock intent. Availability checks share a maximum 50 ms query result; activation always queries current aim again. Both component and actor are resolved by indexed identity on each use. Session reset and settings Apply clear this cache. Queries only occur in response to ability checks; no timer or idle search is added. Logging aggregates `focusQueries`, `focusTargets` and `focusUs`. The optional code contract validates the relevant validator/planner/getter/execution functions and level/type accessors separately; failure leaves camera features available.
